01AgentOps, the closest match

Define what an agent may do. Enforce it before the money moves.

A wallet gives an agent the ability to pay. AgentOps decides whether it is allowed to. Every action an agent attempts runs one fail-closed path.

  1. Verify the agent's identity
  2. Evaluate policy
  3. Check budget
  4. Escalate to a human over a threshold
  5. Execute and settle
  6. Write an evidence record that links intent to settlement

Highlighted steps are the policy gate. If any step cannot answer, the action is denied.

AgentOps demo

What I built

  • The architecture, the payment and backend services, and the client, as lead architect and engineer.
  • A policy API and a console policy editor with a visual builder, plus a chatbot that creates a policy from speech or a typed command. The hard part was showing IAM-style depth without making it hard to use.
  • A hosted MCP server that agents use, the same one human operators govern.
  • Real-time review of agent actions, shown as a live stream while many agents run at once.
  • Rails chosen by the relationship: x402 and Gateway for machine-to-service payments, Permit2 for bounded agent-to-agent spending, escrow for a first deal with an unproven counterparty.

Shown running

  • Policy-controlled hiring of another agent.
  • Second-hop delegation, where an agent hires another agent on its own authority.
  • Approval-gated cross-chain execution.
  • Capital revoked from an agent and recovered.

Before building it I studied how x402, MPP, Stripe's agent payments and AWS AgentCore handle authorization.

Limits

Testnet only (Arc Testnet and Base Sepolia). The policy surface covers payments: identity, budget and approvals.

It controls what an agent may do, not where the agent runs. Extending the same decision path to data access and tool calls is the work I would want to do at Firma.

02GuardianKane, why enforcement cannot live with the agent

An agent's "done" has to be something it proves.

GuardianKane blocks a Claude Code agent from finishing until a real browser replays a test and an independent defect sweep passes. Three failed attempts escalate to a human, not another loop.

460+unit tests on the harness
4paired A/B builds, same PRD with and without the gate
3strikes, then a human decides
12numbered build phases

Then I audited the verifier

The verifier is itself an agent, so I wrote up where it fails. Across the 13 ORBITAL tasks, 8 failed a check at least once, and only one was a real app bug. Six needed human-reviewed overrides, and the verifier's own triage marked all six as automation bugs, not app bugs. The attempts counter lived in a tracker file the agent could edit, and it went backwards in the log.

A cap the capped party can edit is a suggestion.From "Who Verifies the Verifier?", my write-up of that audit

That is the design rule behind AgentOps: the gate runs in a service the agent cannot write to.

Limits

Four builds is a small sample, and the gap shrinks on simple PRDs. In my own results two of the four showed no confirmed divergence.

The verifier is slow and can misjudge, which is why overrides stay with a human.

03Loom, parallel agents acting on stale state

Agents that pass alone and break when merged.

Agent A changes a function's contract, agent B writes a new caller against the old one, git sees no conflict, and the tests fail only after the merge. Loom keeps the call graph, in-flight edits, leases and test evidence in one graph, and tells the agents whose code depends on a change, mid-work.

0 to 24merges passing out of 36 Django task pairs, without and with Loom
12 of 12signature changes merged
0double lease grants in 50 agents and 10,000 attempts, against 2,332 with the check off
108real runs across blind, oracle and live
Limits

One run per pair, one model (Claude Haiku), one codebase (Django), and a custom harness that differs from the STALE-bench protocol.

Return-type changes passed only 3 of 12. In 10 of the 12 failures the agent understood the warning and chose to wait, a hypothesis from a handful of transcripts, not a controlled result.

04Rust, and systems that ran with real clients

I have operated this kind of system, not only demoed it.

PayZoll, lead architect

  • Rebuilt the Stellar Disbursement Platform from single tenant into a multi-tenant system running batch payroll for many organizations, with signing keys derived in AWS KMS instead of stored.
  • Wrote the Soroban contract services and the channel-account workers in Rust. Soroban's authorization trees let one channel account fan out into many parallel contract calls, which took throughput from 8 to a stable 120 transactions per block (220 at peak).
  • Our first client found the status model too coarse, and payments were being marked done too early. I replaced it with an 8-state lifecycle, added idempotency keys so no batch runs twice, and built a recovery service that retries a failed payment 3 times and then returns the funds.
  • One client's isolation requirement moved the Go platform fork from one deployment per customer to one shared, data-isolated database.
  • Led two engineers and ran live schema migrations for early clients.

05The gap

I have not built sandbox isolation.

Everything above enforces at the API and policy layer. Firma enforces wherever agents run, and that includes the sandbox.

I designed, but did not build, a microVM environment for a challenge: capture how software runs on one machine and replay it on another. The reasoning was that a container shares the host kernel and a VM does not, so a VM carries the environment more completely. It stayed a design. What I have is a clear picture of where that boundary is hard. What I have not done is build it.

It is the first thing I would learn at Firma, in Rust, with the policy gate I already know in front of it.
